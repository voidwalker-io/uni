Kapitel 01Kontrollflussgraph (CFG)

Blatt 1 · Aufgaben 1.1, 1.2, 1.4

Wozu Programmanalyse überhaupt?

Programmanalyse hilft, Code zu verstehen, seine Korrektheit zu prüfen, Tests abzuleiten und ihn zu optimieren. CFG, DFG, PDG und SDG sind statische Analysen: Man liest nur den Code und führt ihn nicht aus. (Dynamische Analyse, also Debugger und Tests, kommt in Kapitel 06 bis 08.)

Was ist ein CFG?

Ein Kontrollflussgraph stellt eine Methode als gerichteten Graphen dar:

  • Knoten = eine Anweisung (Statement). Frage: Was wird gemacht?
  • Kante = möglicher Kontrollfluss. Frage: Was kommt als Nächstes?

Man benennt die Knoten nach der Zeilennummer: S3 ist die Anweisung in Zeile 3. Ein Knoten mit zwei ausgehenden Kanten ist eine Verzweigung (Prädikat, Bedingung). Seine Kanten beschriftet man mit C und ¬C (oder true/false, T/F).

Merke: Was ist ein Knoten, was nicht?
  • Jede ausführbare Anweisung ist ein Knoten: Zuweisungen, Aufrufe, return, break, Bedingungen von if/while/for/switch.
  • Der Methodenkopf ist der Startknoten (bei Parametern dort, wo sie „definiert“ werden).
  • Keine Knoten: Deklarationen ohne Wert (int result;), else, geschweifte Klammern, Leerzeilen.
  • Ausnahme: Die letzte schließende Klammer darf als Endknoten dienen, damit alle Pfade an einem Punkt enden (wenn die Methode kein return am Ende hat).
  • Jede Bedingung (if, while, for) hat genau zwei ausgehende Kanten, C und ¬C. Ein switch hat eine Kante pro case plus default.
  • Jeder Knoten hat einen Nachfolger, außer Return-Knoten und Endknoten.

Rezept: Code → CFG in fünf Schritten

  1. Zeilen nummerieren und jede relevante Anweisung als Sn notieren.
  2. Verzweigungen markieren: if, for, while, do-while, switch. Diese Knoten bekommen mehrere Ausgänge (in den Tutorien rosa eingefärbt).
  3. Normalen Fluss zeichnen, von oben nach unten.
  4. Sprünge ergänzen: Rückkanten der Schleifen, break, continue, return.
  5. Kontrollieren: Sind alle Verzweigungskanten beschriftet? Hat jeder Knoten einen Nachfolger außer dem Ende? Laufen beide Zweige eines if wieder zusammen?

Die Muster je Konstrukt

Fast jede Klausuraufgabe ist eine Kombination dieser sechs Bausteine. Präge dir die Form ein.

Merke: Sprunganweisungen
  • return → Methode endet sofort. Der Knoten hat keinen Nachfolger (in den Tutorien mit doppeltem Rand markiert).
  • break → springt zur ersten Anweisung nach der innersten Schleife bzw. nach dem switch.
  • continue → springt zum nächsten Durchlauf: bei while zur Bedingung, bei for zum Update (i++), nicht zur Bedingung.
  • switch ohne break (fall-through) → ein case läuft einfach in den nächsten weiter (rote gestrichelte Kante oben). Beim neuen Pfeil-switch case "1" -> … gibt es kein fall-through.
  • for zerfällt in drei Knoten: Initialisierung (S7.1), Bedingung (S7.2), Update (S7.3 oder als eigener Knoten am Schleifenende). Die Rückkante geht vom Update zur Bedingung.

Typische Fehler beim CFG
  • Die Rückkante einer Schleife geht zur Bedingung, nicht zum ersten Knoten des Rumpfes (Ausnahme: do-while).
  • Nach return mid darf keine Kante weitergehen.
  • else ist kein eigener Knoten. Bei else if ist das zweite if der Knoten (hier S11).
  • Beide Ausgänge jeder Bedingung beschriften. Fehlende Beschriftung kostet in der Klausur Punkte.

Hier bekommst du einen Graphen und sollst daraus strukturierten Java-Code machen. Arbeite die drei Fragen aus dem Tutorium der Reihe nach ab:

Kapitel 02Datenflussgraph (DFG)

Blatt 1 · Aufgaben 1.3, 1.5 · Grundlage für Kapitel 03 und 08

Ein DFG ist ein CFG, an dessen Knoten zusätzlich steht, welche Variablen dort geschrieben und gelesen werden. Ziel: jede Variable von ihrer Definition bis zu ihrer Benutzung verfolgen. Man braucht das zum Fehlersuchen (z. B. Variable wird nie benutzt), für die formale Verifikation und später für Datenfluss-Testkriterien.

Merke: die drei Mengen pro Knoten n
  • DEF(n): Variablen, die in n einen Wert bekommen. Links vom =, außerdem Parameter im Startknoten, i++, x += 1.
  • C-USE(n) (computational use): Variablen, die zum Rechnen oder Weitergeben gelesen werden. Rechts vom =, in return, in System.out.println(…), als Methodenargument, als Array-Index a[i].
  • P-USE(n) (predicate use): Variablen, die in einer Bedingung gelesen werden: <, >, ==, != oder ein boolean allein wie if (flag).
Die drei Sonderfälle, die immer abgefragt werden
  • x = x + 1, x++, x += 1: x ist DEF und C-USE zugleich (erst lesen, dann schreiben).
  • Reiner Vergleich wie if (num < 10): num ist nur P-USE.
  • Wird in der Bedingung gerechnet, z. B. if (a[i] > lim) oder n % 2 == 0: erst wird a[i] geholt (a und i gelesen → C-USE), dann verglichen (→ P-USE). Laut Tutorium daher C-USE und P-USE.

Def-Use-Paare und Datenabhängigkeit

Ein Paar (A, B) für Variable v existiert, wenn

  1. A die Variable v definiert (v ∈ DEF(A)),
  2. B die Variable v verwendet (C-USE oder P-USE), und
  3. es einen Pfad von A nach B gibt, auf dem v nicht neu definiert wird (ein „definitionsfreier“ oder „Def-Use-Pfad“).

Dann ist B datenabhängig von A. Die Faustfrage lautet: Wer hat v zuletzt geschrieben, bevor B sie liest? Bei Schleifen gibt es oft mehrere Antworten.

Beispiel aus dem Tutorium

1int count(int[] a, int n) {
2    int count = 0;
3    int i = 0;
4    while (i < n) {
5        if (a[i] > 0)
6            count = count + 1;
7        i = i + 1;
8    }
9    System.out.println(count);
10}

Def-Use-Paare für count: (2,6), (2,9), (6,6), (6,9). Warum (6,6)? Im nächsten Schleifendurchlauf liest Zeile 6 den Wert, den sie im letzten Durchlauf selbst geschrieben hat.

Rezept: DFG in fünf Schritten

  1. CFG zeichnen (Kapitel 01).
  2. DEF: Bekommt eine Variable hier einen Wert?
  3. C-USE: Wird sie zum Rechnen oder Ausgeben gelesen?
  4. P-USE: Wird sie in einer Bedingung gelesen?
  5. Def-Use-Paare: Für jede Verwendung fragen, welche Definitionen sie ohne Zwischen-Neudefinition erreichen.

Am Papier schreibt man DEF/C-USE/P-USE entweder neben die Knoten oder in eine Tabelle mit den Spalten S# | def | c-use | p-use. Die Tabelle ist schneller und übersichtlicher.

Kapitel 03Program Dependence Graph (PDG)

Blatt 2 · Aufgaben 2.1, 2.2, 2.3

Der CFG beantwortet „Was kommt nach was?“. Der PDG beantwortet „Was bestimmt was?“. Er kennt nur zwei Kantenarten:

  • Kontrollabhängigkeit (KD), durchgezogener Pfeil. Frage: Welche Anweisung A entscheidet, ob B überhaupt ausgeführt wird?
  • Datenabhängigkeit (DD), gestrichelter Pfeil. Frage: Welche Anweisung A kann den Wert bestimmen, den B liest?
Merke: Definitionen nach Horwitz (wörtlich lernen)

Knoten sind Anweisungen, in denen Variablen initialisiert oder referenziert werden, plus ein Entry-Knoten für den Methodenkopf.

Kontrollabhängigkeit: Knoten B ist kontrollabhängig von Knoten A, wenn entweder A der Entry-Knoten ist und B in keiner Schleife oder Bedingung liegt, oder wenn A ein Kontrollprädikat (if, while, for, switch) ist und vom Ergebnis von A abhängt, ob B ausgeführt wird. Die Kante wird mit dem Wert beschriftet, bei dem B ausgeführt wird (T/F bzw. case).

Datenabhängigkeit: Knoten B ist datenabhängig von Knoten A, wenn A eine Variable v definiert, B die Variable v verwendet und es einen Pfad von A nach B gibt, auf dem v nicht neu definiert wird (Def-Use-Pfad).

Kapitel 04Slicing nach Weiser

Blatt 2 · Aufgaben 2.4, 2.5

Merke: Definition aus der VO

„Ein Slice S ist durch die Streichung derjenigen Anweisungen eines Programms definiert, die nicht relevant in Bezug auf die ausgewählten Variablen V an der gewählten Stelle n sind.“ Schreibweise: S(n, {V}) = Menge von Anweisungen. (n, V) heißt Slice-Kriterium.

Backward Slice

Alle Anweisungen, die die Variablen V an Stelle n beeinflussen. Frage: Woher kommt dieser Wert?

Vorgehen: Im PDG beim Kriterium starten und alle Pfeile (KD und DD) rückwärts gehen, bis nichts Neues mehr dazukommt.

Forward Slice

Alle Anweisungen, die von V an Stelle n beeinflusst werden. Frage: Was ist betroffen, wenn ich diese Zeile ändere?

Vorgehen: Beim Kriterium starten und alle Pfeile vorwärts gehen.

Das Slice-Kriterium gehört immer dazu. Beim Backward Slice gehört der Entry-Knoten praktisch immer dazu (alles hängt per KD an ihm).

Mini-Beispiel aus der Klausurvorbereitung

1void login(int attempts, boolean admin) {
2    boolean locked = false;
3    int bonus = 0;
4    if (attempts > 3)
5        locked = true;
6    if (admin)
7        bonus = 10;
8    int level = bonus + 1;
9    if (!locked)

  • Backward S(11, {locked}) = {S1, S2, S4, S5, S11}. S11 liest locked → DD von S2 und S5. S5 hängt per KD an S4. Alle hängen per KD am Entry S1.
  • Forward S(5, {locked}) = {S5, S9, S10, S11}. S5 schreibt locked → S9 und S11 lesen es (DD). S10 hängt per KD an S9.

Kapitel 05System Dependence Graph (SDG)

Blatt 3 · Aufgaben 3.1, 3.2, 3.3

Ein PDG beschreibt eine Methode. Sobald Methoden einander aufrufen, braucht man den SDG: alle PDGs zusammengeklebt, plus Extra-Knoten für die Parameterübergabe. Er berücksichtigt den Aufrufkontext und erlaubt interprozedurales Slicing.

Die Knotenarten

Merke: Zählregeln
  • 1 Methode = 1 Entry, egal wie oft sie aufgerufen wird. Auch bei Rekursion wird die Methode nur einmal gezeichnet.
  • 1 Aufruf im Code = 1 Call-Knoten (mit eigenen Actual-in/out-Knoten).
  • Ein return r; wird direkt zum Formal-out-Knoten r_out = r, kein eigener S-Knoten.
  • Wird das Ergebnis nicht in einer Variable gespeichert (z. B. if (isWarm(v))), heißt der Actual-out-Knoten _ = _out, weil links kein Name stehen kann.

Rezept: SDG bauen

  1. Für jede Methode den PDG zeichnen (Entry, Anweisungen, KD). Jeder Aufruf wird ein Call-Knoten.
  2. Parameterknoten ergänzen: beim Aufrufer Actual-in (pro Argument) und Actual-out (pro Rückgabe), beim Aufgerufenen Formal-in und Formal-out. KD vom Call bzw. Entry zu ihnen.
  3. DD-Kanten innerhalb jeder Methode (wie PDG), inklusive „wer liefert den Wert fürs Actual-in“ und „wer liest das Actual-out“.
  4. Aufruf-Kanten: Call → Entry.
  5. Par-in (Actual-in → Formal-in) und Par-out (Formal-out → Actual-out).
  6. Summary-Kanten: Actual-in → Actual-out, wenn es im Callee einen Abhängigkeitspfad vom Formal-in zum Formal-out gibt.
Verschachtelte Aufrufe und Rekursion

Ruft rectangleArea selbst multiply auf, ist rectangleArea gleichzeitig Callee (für main) und Caller (für multiply). Es bekommt also Formal-Knoten und einen eigenen Call-Knoten mit Actual-Knoten. Bei Rekursion (step(n-1) in step) gibt es einen Entry, aber zwei Call-Knoten (einen in main, einen in step), und die Aufruf-Kante des inneren Calls zeigt zurück auf denselben Entry.

Objekte und Felder im SDG (Aufgabe 3.2)

Merke: So werden Objekte behandelt
  • Felder sind versteckte Parameter. Liest eine Methode ein Feld, bekommt sie einen Formal-in-Knoten dafür (b_in). Schreibt sie es, bekommt sie einen Formal-out-Knoten (b_out). Auch wenn das Feld nicht in der Parameterklammer steht, es gehört zum Objekt und wird beim Aufruf unsichtbar mitgegeben.
  • Ein Konstruktor, der Felder nur setzt, hat nur Out-Knoten (a_out, b_out), keine In-Knoten.
  • Eine Methode wie add(int x) { v = v + x; } liest den alten Wert (v_in) und gibt den neuen zurück (v_out).
  • Jeder Aufruf auf jedem Objekt bekommt einen eigenen Call-Knoten mit Actual-Knoten für die Felder dieses Objekts (ba.b_in vs. o.b_in). Jede Methode hat aber trotzdem nur einen Entry.
  • Felder, die eine aufgerufene Methode liest oder schreibt, „vererben“ sich nach oben: Ruft m1 die Methode vm auf, die a schreibt, braucht auch m1 ein a_out.
11public void m2(int i) { b = b + i; }
15public void m1() {
16    if (b > 0) {
17        vm();
18    }
19    b = b + 1;
20}
22public void vm() { a = a + b; }

Wörtliche Erklärung für die Knoten 15–19 (m1)

  • 15 Entry m1. m1 liest b (Zeile 16, 19) und über vm auch a und b. Daher Formal-in a_in und b_in. m1 schreibt b (Zeile 19) und über vm a, daher Formal-out a_out und b_out. Entry ist KD-Vorgänger von a_in, b_in, S16, S19, a_out, b_out.
  • S16 if (b > 0). P-USE von b. DD-Kante von b_in nach S16. S16 ist das Prädikat für den Aufruf in Zeile 17 (KD, T).
  • 17 Call vm. Actual-in a_in = a und b_in = b (beide per DD von den Formal-in-Knoten von m1 versorgt), Actual-out a = a_out. Par-in zu den Formal-in-Knoten von vm, Par-out von vm.a_out zurück. Summary-Kanten a_in → a_out und b_in → a_out, weil in vm a = a + b gilt.
  • S19 b = b + 1. C-USE von b: DD von b_in (vm ändert b nicht, also keine Neudefinition dazwischen). DEF von b: DD nach b_out.
  • a_out von m1 bekommt DD von zwei Stellen: vom Actual-out in 17 (wenn vm lief) und direkt von a_in (wenn b <= 0, dann bleibt a unverändert).

Im main gibt es fünf Call-Knoten: new Base() für o und für ba (nur Actual-out a, b), ba.m1() (in/out ba.a, ba.b), ba.m2(1) (in i=1, ba.b; out ba.b) und o.m2(1) (in i=1, o.b; out o.b). DD verbindet die Feldwerte desselben Objekts von Aufruf zu Aufruf, z. B. ba.b aus ba.m1() → ba.b_in von ba.m2(1).

Interprozedurales Slicing: der Zwei-Phasen-Algorithmus

Würde man im SDG einfach alle Pfeile rückwärts gehen, könnte man über einen Aufruf in die Methode hinein- und bei einem anderen Aufrufer wieder hinausgehen. Das ist ungenau (falscher Aufrufkontext). Deshalb zwei Durchläufe:

DurchlaufStartKanten rückwärts folgenRichtung
DL1Knoten des Slice-Kriteriumsalle außer Par-outgeht rauf: nur Aufrufer werden besucht
DL2alle Knoten aus DL1alle außer Aufruf und Par-ingeht runter: nur aufgerufene Methoden werden besucht

Slice = DL1 ∪ DL2. Die Summary-Kanten sorgen in DL1 dafür, dass Abhängigkeiten „durch“ einen Aufruf hindurch berücksichtigt werden, ohne in die Methode hineinzugehen.

Beispiel aus der Klausurvorbereitung

Im isEven-Programm mit zwei Aufrufen (e1 = isEven(x), e2 = isEven(y), Ausgabe von e1 in S6) ergibt Slice(6, {e1}) = {1 Entry main, S2, 4 Call, n_in = x, e1 = r_out, S6} aus DL1 und {10 Entry isEven, n = n_in, S11, r_out = r} aus DL2. Alles rund um y und den zweiten Aufruf fällt weg, obwohl dieselbe Methode aufgerufen wird. Genau das leistet der Zwei-Phasen-Algorithmus.

Kapitel 08White-Box-Testen und Überdeckung

Blatt 5 · Aufgaben 5.1 bis 5.5 · laut Plan eher Endklausur, hier zur Sicherheit vollständig

Beim White-Box-Testen schaut man in den Code und fragt: Welche Teile des Codes haben meine Tests überhaupt ausgeführt? Das Maß dafür heißt Überdeckung (Coverage). Testdaten kommen aus dem Code, erwartete Resultate weiterhin aus der Spezifikation.

Anweisungs- und Zweigüberdeckung (5.1)

public static int remainingAttempts(int failedAttempts, boolean trusted) { // S0
    int remaining = 3;                                   // S1
    if (trusted) {                                       // S2
        remaining = 5;                                   // S3
    }
    if (failedAttempts > 0) {                            // S4
        remaining = remaining - failedAttempts;          // S5
    }
    return Math.max(0, remaining);                        // S6
}
Merke

Anweisungsüberdeckung (Statement Coverage, C0) = ausgeführte Anweisungen / alle Anweisungen.

Zweigüberdeckung (Branch Coverage, C1) = durchlaufene Entscheidungsausgänge / alle Entscheidungsausgänge. Jedes if hat zwei Ausgänge (true, false), auch wenn der false-Zweig leer ist.

100 % Zweig ⇒ 100 % Anweisung, aber nicht umgekehrt.

Musterlösung 5.1

T1: failedAttempts = 1, trusted = true. Erwartet: 5 − 1 = 4. Knotenfolge S0, S1, S2, S3, S4, S5, S6.

  • Anweisungsüberdeckung (gezählt S1, S3, S5, S6): 4/4 = 100 %
  • Zweigüberdeckung (S2-true, S2-false, S4-true, S4-false): nur die beiden true-Ausgänge, also 2/4 = 50 %

Ergänzung auf 100 % Zweig: ein einziger Test T2: failedAttempts = 0, trusted = false → erwartet 3. Er nimmt beide false-Ausgänge. {T1, T2} = 4/4 = 100 %. Mehr braucht es nicht, weil jeder Test pro Entscheidung nur einen Ausgang nehmen kann und T1 schon beide true-Ausgänge hat.

Laut Spezifikation zusätzlich: ausgeschöpft T3: (3, false) → 0; überschritten T4: (4, false) → max(0, −1) = 0.

5.1.4: T1 führt jede Anweisung aus, aber nie einen leeren false-Zweig. Ein Fehler, der nur auftritt, wenn ein if nicht betreten wird (z. B. falscher Startwert in S1 für normale Konten), bleibt unentdeckt. Auch 100 % Zweigüberdeckung beweist keine Fehlerfreiheit: Sie sagt nichts über konkrete Werte (Grenze 3 vs. 4), über Kombinationen von Zweigen (Pfade), fehlende Funktionalität oder falsche Assertions. Tests können nur die Anwesenheit von Fehlern zeigen, nie ihre Abwesenheit.

Bedingungsüberdeckung und MCDC (5.2)

if (active && (passwordCorrect || recoveryCodeValid)) return true;
return false;

A = active, B = passwordCorrect, C = recoveryCodeValid, D = A ∧ (B ∨ C). Die atomaren Bedingungen sind A, B, C; die Entscheidung ist D.

  • Short-Circuit (X = nicht ausgewertet): Ist A falsch, wertet && den Rest nicht aus. Ist B wahr, wertet || C nicht aus. Es entstehen nur 4 verschiedene Auswertungsabläufe: (F,X,X), (T,F,F), (T,F,T), (T,T,X).
Merke: die Bedingungskriterien
  • Einfach-Bedingungsüberdeckung: jede atomare Bedingung ist mindestens einmal true und einmal false. Garantiert nicht, dass D beide Werte annimmt.
  • Mehrfach-Bedingungsüberdeckung: alle 2ⁿ Kombinationen. Gründlich, aber explodiert.
  • MCDC (Modified Condition/Decision Coverage): Für jede atomare Bedingung gibt es ein Testpaar, in dem nur diese Bedingung wechselt und dadurch D wechselt. Damit ist gezeigt, dass jede Bedingung das Ergebnis unabhängig beeinflusst. Minimal oft n + 1 Tests.

  1. Für Bedingung A: Suche zwei Zeilen, die sich nur in A unterscheiden und verschiedenes D haben.
  2. Dasselbe für B und C.
  3. Wähle die Paare so, dass sie sich möglichst viele Zeilen teilen.

Ausgewertet true und false? A: T in 5, 6, 7 und F in 3. B: F in 5, 6 und T in 7 (in Zeile 3 maskiert). C: F in 5, T in 6. Alles erfüllt. Zweigüberdeckung ist mit D = T (6, 7) und D = F (3, 5) ebenfalls 100 %, Einfach-Bedingungsüberdeckung auch.

Mutationstesten (5.5)

Man baut absichtlich kleine Fehler (Mutanten) in den Code und schaut, ob die Tests sie bemerken. Ein Test tötet (eliminiert) einen Mutanten, wenn sein Ergebnis anders ist und die Assertion fehlschlägt. Mutation Score = getötete Mutanten / alle (nicht äquivalenten) Mutanten.

  • Zusatztest gegen M1: (0, false) → Original 3, M1 liefert 4 → getötet.
  • M2 ist äquivalent: Für failedAttempts > 0 sind beide Bedingungen gleich. Für 0 rechnet der Mutant remaining − 0, also denselben Wert. Negative Werte sind nicht spezifiziert. Kein erlaubter Input unterscheidet ihn, also kann ihn kein Test töten.
  • Warum 100 % Anweisungsüberdeckung nicht reicht: T1 führt S1 aus, aber der veränderte Wert wird von S3 überschrieben und erreicht nie die Ausgabe. Ein Mutant wird nur erkannt, wenn er erreicht wird, den Zustand infiziert und dieser Unterschied bis zur Ausgabe propagiert (RIP-Modell), und eine Assertion genau diesen Wert prüft.
